Продолжи работу с USB-модемом ZTE MF79U на Windows в виртуальной машине.

Цель и разрешения:
Пользователь разрешил обновить/изменить прошивку, чтобы заработали приём и чтение SMS через CLI/API для будущей автоматической пересылки. Работа ещё не завершена. Модем НЕ прошивали, режим USB НЕ переключали, разделы НЕ стирали. Перед записью нужно получить совместимый образ и сделать проверенную резервную копию как минимум rootfs и nvrofs. Не менять IMEI, TTL, APN или диапазоны ради сторонних задач. Не отправлять и не удалять SMS. Секреты не выводить в логи; пароль веб-панели пользователь введёт локально.

Подтверждено на физическом модеме через его API на Mac:
- USB VID:PID 19d2:1405, USB имя ZTE Mobile Boardband.
- hardware_version: MF79U-HW1.0.
- wa_inner_version: BD_XCBZHKMF79UV1.0.0B03.
- web_version: WEB_XCBZHKMF79NV1.0.0B02.
- cr_version: пусто.
- modem_main_state: modem_init_complete.
- После регистрации: оператор epic, сеть GSM/EDGE; PPP отключён.
- Адрес веб-панели http://192.168.0.1, на Mac был интерфейс en10 с DHCP 192.168.0.169.
- На Mac Wi-Fi подняли выше ZTE в порядке сетевых служб, чтобы модем не забирал основной маршрут.

SMS-проблема:
Пользователь отправил тестовое входящее SMS. После успешной авторизации API возвращал messages: [] как для mem_store=1 (память устройства), так и для mem_store=0 (SIM). sms_capacity_info: sms_nv_total=0, sms_sim_total=0, sms_nv_rev_total=-2, sms_nv_send_total=-1, sms_nv_draftbox_total=-2; у SIM аналогично. sms_unread_num и соответствующие dev/sim поля = -1. В js/config/config.js HAS_SMS=false, модельная конфигурация его не переопределяет. Это признаки недоступной SMS-подсистемы; пустой список не доказывает отсутствие сообщений.

API, сверенный с JS этой прошивки:
1. GET /goform/goform_get_cmd_process?isTest=false&cmd=LD
2. POST /goform/goform_set_cmd_process, form-urlencoded:
   isTest=false&goformId=LOGIN&password=<SHA256(SHA256(password)+LD)>
   Оба SHA256 — HEX В ВЕРХНЕМ РЕГИСТРЕ. Сохранить cookie в текущей сессии. result=0 подтверждён, loginfo=ok.
3. GET /goform/goform_get_cmd_process?isTest=false&cmd=sms_data_total&page=0&data_per_page=500&mem_store=1&tags=10&order_by=order+by+id+desc
   Referer: http://192.168.0.1/index.html, X-Requested-With: XMLHttpRequest.
   tags=10 — список, используемый штатным UI. mem_store=0 — SIM.
   Содержимое SMS обычно hex UTF-16BE. Обработать кириллицу и surrogate pairs.
4. GET с cmd=sms_capacity_info — проверка готовности хранилища.

Текущие файлы:
На Mac создан CLI zte-sms.py (передать отдельно). Работает на Python standard library, пароль запрашивается --login или берётся из --password-file/--password-stdin. Cookie только в памяти. При пустом списке и отрицательных SMS-счётчиках выдаёт ошибку, чтобы автоматизация не считала это пустым входящим списком.

Первые действия на Windows:
1. Проверить ОС/архитектуру, проброс USB и идентификаторы устройства.
2. Проверить доступ к http://192.168.0.1 именно через модем и сохранить основной интернет VM другим интерфейсом.
3. Получить архивы от пользователя/источника, проверить, что это настоящие архивы, исследовать содержимое.
4. Установить подходящие драйверы и подготовить бэкап/восстановление.
5. Снять бэкап разделов с размерами и контрольными суммами; хранить его локально, без публикации уникальных NV-данных.
6. Записать только совместимое необходимое изменение, вернуть user mode, проверить сеть и SMS API.
7. Успех: корректная SMS-вместимость/счётчики и реально полученное тестовое сообщение, читаемое через CLI. Не заявлять успех по одному запуску прошивальщика.
