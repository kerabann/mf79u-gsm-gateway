# MikoPBX и автономный MF79U

Сверено 2026-10-10. Общая сводка: [STATUS.md](../../firmware/mf79u/STATUS.md).
USB/ADB/SIP восстановлены. Persistent CS→SIP/PBX входящий тест подтверждён
пользователем: тон, эхо и своевременный отбой; временная echo extension и
маршрут удалены/восстановлены. SIP voice offer теперь без ненужного RTT:
все пять кодеков и длинный Caller ID помещаются в один LAN UDP payload.
Реальный AUTO failed-IMS→CS fallback и fresh boot проверены отдельно.
Отдельный CS emphasis дал более ясное эхо; исправлены ложное истечение lease
при DSP bootstrap и отложенный запуск входящего PCM. Последний входящий тест:
тон, эхо и отбой подтверждены, reboot не было. AUTO/IMS снова проверен после
финальной перезагрузки. IMS audio hashes и общий FIR не изменились:
[CS-AUDIO.md](../../firmware/mf79u/CS-AUDIO.md). Историческое
состояние недоступного USB на2026-10-08 не является текущим.

MikoPBX 2026.5.6 ARM64 запущена в Docker Desktop. Использован digest ARM64,
не плавающий latest. Данные сохраняются в volumes `mf79u-pbx_cf` и
`mf79u-pbx_storage`. Compose: `compose.yaml`.

`172.29.0.1`. На аудите identify содержит отдельные /32 для 172.29.0.1, 172.20.0.1 и

расписание MikoPBX больше не перехватывает SIM-вызовы сообщением «нерабочее
время». Расписания остальных провайдеров не менялись.

## Caller ID, calls/CDR и SMS через PBX (2026-10-08)

Провайдер использует cid_source=pai и trust_id_inbound=yes. Входящий номер
из From/P-Asserted-Identity отображается отдельно от имени учётной записи
транка; Privacy id даёт Anonymous. Persistent custom-файлы42/45 хранят
наши отмеченные dialplan/PJSIP fragments, после генерации выполняется reload.
Исторические CDR с утраченным номером не переписывались выдуманными данными.
Отказ на звонящем телефоне корректно даёт NOANSWER и billsec0; несколько
записей одного linkedid отражают разные ноги вызова.

Исходящий route22 принимает цифровые внешние назначения ([0-9]{3}, остаток
не ограничен), сохраняет цифры без trim/prepend; внутренние extensions имеют
приоритет. Пользователь подтвердил исходящее ringing и ранее рабочий incoming
звонок, затем объявил задачу calls/history выполненной. Новые тестовые вызовы
для документации не требуются. Read-only audit подтвердил эти поля route/provider.

Входящий SIP MESSAGE идёт в mf79u-sms-incoming →201 с реальным отправителем.
Authenticated MESSAGE от201 (включая его TLS/WS endpoints) попадает через
mf79u-sms-outgoing/mf79u-sms-send в SIP-TRUNK-51091984, только для phone URI.
Пользователь подтвердил обычные PBX сообщения. Последний отдельный GSM/EDGE
roaming fallback доказал cellular storage/PBX ACK без IMS; конечный Linphone
тогда был недоступен, поэтому его display не подтверждён для этого теста.
Подробнее: [SMS-SIP.md](../../firmware/mf79u/SMS-SIP.md).

В Linphone account domain должен быть 192.168.0.169 без :port; registrar/proxy
sip:192.168.0.169:5060 / UDP. Старый domain с :port приводил к неправильному
Request-URI при вызовах, хотя REGISTER/MESSAGE работали; старый профиль
отключён и сохранён для истории. Credentials остаются приватными.

Guarded изменения конфигурации, только когда изменения действительно нужны:

```sh
python3 outputs/mikopbx/configure-sip-messages.py --apply
python3 outputs/mikopbx/configure-call-routing.py --apply
```

Оба helper проверяют отсутствие разговоров, сохраняют защищённые backups,
не создают звонков/SMS и не редактируют CDR. --restore восстанавливает исходные
поля; реальные rollback проверки не выполнены. Не импортировать configure.py:
он содержит top-level изменения настроек/аккаунтов. Не запускать его как
routine startup для существующей настроенной PBX.

## Исторический результат 2026-10-06

MikoPBX показывает SIP endpoint модема как `Avail`, RTT примерно 2–4 мс.
Реальный исходящий вызов из PBX прошёл через модем и SIM; пользователь ответил
и подтвердил слышимость тестовых сигналов. SIP вызов установлен, PCM содержит
807 кадров модем→PBX и 682 PBX→модем; ненулевых 741 и 363 соответственно.
Это доказывает доставку тестового звука до телефона и обратную аудиоактивность,
но само по себе не доказывает разборчивость обратной речи.
Звук исходящего разговора не записывался. После отбоя: 0 каналов PBX, транк Avail,
индикатор сети синий, ADB отвечает без перезапуска модема.

Позднее выполнен входящий SIM-вызов с автоответом и записью речи по просьбе
пользователя. Исходный receive WAV: 25.78 с, PCM16 mono 8000 Hz, пик −7.42 dBFS,
RMS −31.05 dBFS, клиппинг 0%. Локальный Whisper small распознал «раз-два-три»,
«проверка» и часть разговорных фраз, с ошибками; это не оценка MOS.
Паузы и возможные пропуски PCM по одному WAV не различить. Оригинал,
транскрипция и измерения: `recordings/mf79u-incoming-20261006-223154/`.
После отбоя подтверждены 0 каналов, транк Avail, синий индикатор. Временное
приложение 880 удалено, маршрут восстановлен на 201; тестовый автоответ выключен.

Для повторной явно запрошенной проверки:

```sh
python3 outputs/mikopbx/record-incoming.py
```

Скрипт ждёт один пользовательский входящий вызов до десяти минут, отвечает,
проигрывает сигнал и записывает максимум 45 секунд, затем восстанавливает
маршрут. Исходящие вызовы не создаёт. WAV на Mac хранится с правами 0600
в каталоге 0700. Распознавание выполнялось локально; звук никуда не отправлялся.

После исправления очередей и тактирования повторная запись 11.04 с показала
0 underflow/overflow в обоих направлениях. Обнаружен операторский режим
AMR-NB 5.15 кбит/с. Измерения, ограничения сравнения и дальнейший путь к
повышению битрейта: [audio-quality.md](audio-quality.md).
Пользователь подтвердил устранение запинаний; глухой тембр сохранился.
Только для отдельно разрешённого legacy RAM/recovery эксперимента
после остановки native supervisor:
`python3 firmware/mf79u/run-pbx-gateway.py --prefer-high-amr`.
SDP/CMR проверяются перед изменением пакетов; принятие запроса сетью и
субъективное улучшение ещё нужно подтвердить входящим звонком.

В первом тесте CLI-команда originate отсутствовала в MikoPBX и вызов не был
создан. `test-call.py` исправлен: использует штатную очередь Asterisk call files,
не повторяет вызовы автоматически, ограничивает тест 45 секундами и завершает
только собственные каналы. Следующий вызов дошёл, но остался без ответа;
последний, явно разрешённый повтор подтвердил звук.

## Обычный запуск, read-only диагностика и остановка

Из текущего корня <checkout>:

```sh
docker compose -f outputs/mikopbx/compose.yaml up -d
docker exec mf79u-mikopbx asterisk -rx 'core show channels count'
docker exec mf79u-mikopbx asterisk -rx 'pjsip show endpoint SIP-TRUNK-51091984'
```

Модем запускает native CP/IMS/SIP сам от init. Mac relay, foreground ADB и
run-pbx-gateway.py не нужны для обычной работы. Docker PBX — выбранный внешний
SIP-сервер, а не часть обязательного runtime модема; в SERVER можно подключить
один клиент непосредственно к устройству. SIP учётные параметры редактируются
в новой WebUI на вкладке SIP. Без готового IMS голос получает 503, SMS fallback
сохраняется при регистрации SIM; GSM voice audio отсутствует.

Для остановки PBX с сохранением данных:

```sh
docker compose -f outputs/mikopbx/compose.yaml stop
```

run-pbx-gateway.py и configure.py использовались на раннем RAM этапе.
Первый допустим только как отдельный recovery experiment после штатного
выключения/cleanup native supervisor. Не запускать второй поверх существующей
конфигурации без проверки его изменений. Прежние connection.json/call-test.json/
integration-result.json — отчёты исторических тестов, не текущий health snapshot.

## Архив ограничений RAM-прототипа0.5 (2026-10-06)

Ниже перечислены ограничения именно старого0.5 этапа; их заменили
нативный автозапуск, WebUI и AMR-WB/FT8. Общие действующие ограничения
— full-image/recovery не проверены, GSM voice audio/EVS отсутствуют,
длительные multi-operator/DTMF проверки не подтверждены.

Постоянная прошивка не записывалась. Offline rootfs 0.5 содержит компоненты,
но запускает автоматически только индикацию; голос пока запускается вручную.
Сетевой PCM включается отдельным `MF79U_PCM_NETWORK=1`. Режим без этого флага
остаётся диагностическим, с тишиной. PCM проходит между двумя локальными UDP
портами модема, 46000/46001; в сеть USB выходит только SIP/RTP через PJSIP.

Входящий SIM-вызов, автоответ PBX и поступление речи в WAV проверены.
Полная оценка качества речи, DTMF между SIM и PBX, AMR-WB, дополнительные вызовы,
восстановление после потери USB и длительная стабильность ещё не проверены.
Шлюз ограничен одним вызовом и 300 секундами на вызов. Native IMS ESP пока
поддерживает UDP, но не TCP. Неизолированный vendor audio-release IPC 4140
требует отдельной доработки перед постоянной эксплуатацией.

Страница управления подключением к PBX будет отдельным следующим этапом.
На том этапе параметры задавались вручную; последующие Control0.10 и PBX
route22 уже реализуют UI и цифровые маршруты. Тогда будущий UI должен был убрать привязку
к единственному тестовому номеру и управлять конфигурацией шлюза.

тома `mf79u-pbx_cf` / `mf79u-pbx_storage`, aliases и опубликованные порты.
Docker Desktop перезапущен; PBX кратковременно была остановлена.

В `~/.docker/daemon.json` настроены `default-address-pools`:
`[{"base":"10.240.0.0/16","size":24}]`, а `bip` — `10.239.255.1/24`.
На момент проверки оба диапазона не пересекались с текущими явными маршрутами
Mac и Docker-сетями. Это не гарантирует отсутствия пересечений при смене VPN.
Новые автоматически выделяемые IPv4 сети используют этот пул; явные Compose
IPAM/subnet его переопределяют. Другие существующие сети не переносились.

Проверено live: Docker info показывает новый пул; default bridge —
`10.239.255.0/24`; временная сеть без `--subnet` получила `10.240.1.0/24`
и была удалена. Ни одна текущая Docker-подсеть не содержит `172.20.10.49`.
WebUI HTTP 200, Asterisk отвечает, 0 active calls, SIP OPTIONS к опубликованному
UDP 5060 вернул 200 OK. Захват только заголовков пакетов подтвердил сохранение
Desktop NAT source `172.29.0.1`, уже включённого в identify. Настройки SIP не менялись.
Транк к модему остаётся Unavailable; реальные звонки/SMS не проверялись.
