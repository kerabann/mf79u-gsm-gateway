# SIP ↔ GSM: назначение блоков аудиотракта

## Отдельный тракт SIP ↔ VoLTE

2026-10-10 добавлена интерактивная анимированная схема «От голоса до VoLTE»
в текущем чате, с двумя режимами: звук и установка звонка. Исходник:
`<local-path>`.

Для нашего VoLTE нельзя переносить предположение о GSM FIFO↔DSP:
`src/ims-software-media.c` кодирует AMR программно на ARM; SIP gateway
передаёт PCM через локальные sockets. Голосовая цепочка:
микрофон → оцифровка → SIP codec → RTP/UDP/IP → сеть → jitter buffer /
SIP decoder → PCM16LE16k → software AMR-WB/NB encoder → новый RTP/UDP/IP
поток через IMS wan5 → сотовый стек → PHY/RF → базовая станция → EPC /
согласованный media endpoint. PBX может находиться на пути медиа либо
разрешать прямое RTP; выбранная схема показывает логическую доставку.

PDCP/RLC/MAC/PHY — общая модель LTE, а не результат инструментирования
каждого внутреннего блока B03. AMR-WB работает с16kHz; AMR-NB требует8kHz
и соответствующего resampling. Для примера20ms AMR-WB при23.85kbit/s
содержит477 речевых битов (около60bytes); RTP/AMR служебные поля и сетевые
заголовки добавляются сверх этого. Исходная частота захвата софтфона может
отличаться от частоты нашего PCM-моста.

SIP/SDP управляет двумя отдельными сторонами звонка: софтфон↔gateway/PBX
и private IMS↔оператор. SIM AKA / IMS registration / согласование / bearer
показаны как упрощённые логические стадии; реальный порядок provisional
responses, preconditions и создания bearer зависит от сети. IMS/P-CSCF
не обязан лежать на пути RTP. Типичная модель QCI5 для IMS signaling,
QCI1 для dedicated voice bearer не утверждает измеренные параметры текущей сети.
Наш userspace IPsec ESP защищает согласованный IMS SIP transport;
это не означает автоматического применения IPsec или SRTP к звуку.

Основания: [CODECS.md](CODECS.md), [AUTONOMOUS.md](AUTONOMOUS.md),
`src/ims-software-media.c`, `src/ims-userspace-ipsec.c`;
[RFC4867](https://www.rfc-editor.org/rfc/rfc4867.html),
[GSMA IR.92](https://www.gsma.com/newsroom/all-documents/ir-92-ims-profile-for-voice-and-sms-v-13-0/).
Новая проверка звонка/модема при создании схемы не выполнялась.
Диаграмма проверена в браузере:20этапов обоих режимов при ширине окна
768/360/320px, без горизонтального переполнения/обрезанных SVG-подписей
и JavaScript ошибок; проверены запуск, пауза, повтор и остановка в конце,
а также dark mode / reduced motion. Изображения для проверки сохранены
в `work/volte-diagram-desktop.png` и `work/volte-diagram-mobile.png`.

## GSM CS: целевой аппаратный тракт

Обновлено: 2026-10-10. Объяснение сверено с STATUS.md / GSM-VOICE.md;
новая проверка физического устройства для этого документа не выполнялась.
Схема ниже — целевой логический тракт, не подтверждение работающего моста.

```text
SIP-клиент / PBX
    ↕ SIP: управление вызовом; RTP: пакеты со звуком
ARM / Linux / SIP gateway
    ↕ декодирование/кодирование SIP-кодека, PCM, согласование частоты
ARM audio port: TX FIFO / RX FIFO
    ↕ внутренний цифровой аудиоинтерфейс I2S / PCM-TDM
DSP audio port / маршрутизация / mixers
    ↕ обработка голоса и сотовый речевой тракт
GSM baseband / TCH / радиотракт
    ↕
Оператор / удалённый абонент
```

Это логические функции; схема не утверждает точную физическую топологию
всех блоков B03 или отдельный чип для каждого блока. Call control идёт
параллельно аудио: DIAL/CONNECT/RELEASE не переносят речевые отсчёты.

| Блок / термин | Для чего нужен |
| --- | --- |
| SIP | Создание, ответ и завершение звонка, согласование параметров медиа. |
| RTP | Передача звука пакетами; jitter buffer сглаживает неравномерность прихода. |
| SIP-кодек | Преобразование PCM в PCMA/PCMU/Opus и другие согласованные форматы и обратно. |
| ARM | Процессор общего назначения; на Linux работает наш SIP gateway и управление. ARM0/ARM1 в audio reports — номера аппаратных аудиопортов, не доказательство двух Linux CPU. |
| PCM | Численные отсчёты звука. Внешний контракт: mono PCM16LE, 16000 Hz, 320 samples/20 ms, 640 bytes звука на блок. Это формат данных, не процессор и не сжатый речевой кодек. |
| FIFO ARM | Аппаратные очереди аудиопорта: TX принимает слова от ARM для передачи; RX хранит принятые слова для ARM. Сглаживают разницу между порционным обслуживанием программой и непрерывной работой порта. |
| I2S / PCM-TDM | Цифровой интерфейс переноса отсчётов. PCM также может означать режим интерфейса с frame sync; это другое употребление того же слова. |
| Master / slave | Master задаёт тактирование интерфейса, slave следует ему. Это роль по clock, а не направление звука. |
| Clock / gate / reset | Тактовый сигнал, разрешение его подачи и сброс блока. Без корректной активации FIFO может не двигаться. |
| Crossbar / route | Выбор соединения между внутренними источниками и приёмниками. Точное рабочее соединение ARM↔DSP на B03 ещё не подтверждено. |
| DSP / Teak | Специализированный процессор обработки сигналов; обслуживает голосовую обработку в модеме. Тон, созданный внутри DSP, позволяет проверить часть пути без ARM audio. |
| AFE | Audio Front End, в наших отчётах профиль/сторона аудиоинтерфейса DSP. Название не доказывает наличие доступного аналогового микрофонного входа. |
| Mixer / gain | Выбор/смешивание источников звука и уровень сигнала. Неверный маршрут или mute может дать тишину при работающем порте. |
| DMA / IRQ | DMA перемещает данные без копирования каждого слова CPU; IRQ сообщает процессору события. Не являются кодеками. Экспериментальные FIFO probes не доказывают production DMA backend. |
| Mailbox / IPC | Передача команд и статуса между подсистемами; команда включения аудио не равна передаче аудиоданных. RPMSG также не следует считать доказанным CS audio transport. |
| TCH / UL / DL | TCH — GSM traffic channel; UL — к оператору, DL — от оператора. TX/RX в отчётах ARM определяются относительно ARM-порта. |

В проверенном reference ISR одно 32-bit FIFO word содержит два PCM16
отсчёта, первый в старшей половине. Поэтому words/s не равно samples/s;
эта аппаратная упаковка не меняет внешний little-endian PCM контракт.
Согласование внешних 16 kHz с исследуемым внутренним 8 kHz трактом требует
отдельного преобразования частоты.

## Подтверждённое состояние по отчётам

- SIP↔PCM проверен изолированным fixture для PCMA/PCMU; это не GSM call test.
- ARM-local loop проверен, но он обходит DSP/GSM.
- DSP-generated tone был слышен удалённому абоненту: DSP→GSM audio работает
  для проверенного маршрута.
- В MT29 FIFO двигался, но RX оставался нулевым. В MT30 при DSP master
  TX остановился после начального заполнения16words, RX0.
- Следовательно рабочий ARM↔DSP audio bridge ещё не доказан. Это также
  не доказывает физическое отсутствие связи. MT31 подготовлен для проверки
  полного reference clock шага, результата live call ещё нет.
- Production CS SIP/PCM backend и автоматический radio fallback не установлены.
